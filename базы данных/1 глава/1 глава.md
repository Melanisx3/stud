# Глава 1. Основные понятия баз данных

## 1. База данных (БД)

**Определение.** База данных (БД) — это организованная совокупность структурированных данных, хранимых в памяти вычислительной системы и отражающих состояние объектов некоторой предметной области, а также связи между ними. БД предназначена для длительного хранения данных и их использования множеством пользователей и приложений.

### Классификация БД

По **модели данных**:
- Иерархические
- Сетевые
- Реляционные
- Объектно-ориентированные
- Объектно-реляционные
- NoSQL (документные, ключ-значение, графовые, колоночные)

По **характеру хранимой информации**:
- Фактографические (краткие сведения об объектах в строго определённом формате)
- Документальные (документы произвольного формата — тексты, изображения, звук)

По **способу распределения данных**:
- Централизованные (хранятся на одном компьютере/сервере)
- Распределённые (данные разнесены по нескольким узлам сети)

По **степени доступа**:
- Локальные (однопользовательские)
- Многопользовательские (в т.ч. с архитектурой «клиент-сервер»)

**Примечание.** Не следует путать БД с СУБД: БД — это сами данные, а СУБД — программное средство для работы с ними (см. п. 4).

---

## 2. Информационная система (ИС)

**Определение.** Информационная система (ИС) — это совокупность взаимосвязанных технических, программных и организационных средств, а также персонала, предназначенная для сбора, хранения, обработки, поиска и выдачи информации, необходимой для решения задач управления и принятия решений в определённой предметной области.

### Классификация ИС

По **степени автоматизации**:
- Ручные
- Автоматизированные (человек + техника)
- Автоматические

По **характеру использования информации**:
- Информационно-справочные (поисковые)
- Информационно-решающие (управляющие, советующие)

По **сфере применения**:
- Экономические (бухгалтерские, финансовые)
- Медицинские
- Технологические (АСУ ТП)
- Обучающие
- Геоинформационные (ГИС) и др.

По **масштабу**:
- Настольные (для одного пользователя)
- Групповые (отдел)
- Корпоративные (предприятие)

**Важно.** ИС — понятие более широкое, чем БД: БД является лишь одним из компонентов (ядром хранения данных) информационной системы. ИС включает также интерфейсы, бизнес-логику, персонал и регламенты работы.

---

## 3. Информационная система по базе данных (ИСБД)

**Определение.** ИСБД — это информационная система, ядром которой является база данных, то есть система, в которой хранение, обработка и предоставление информации организованы через СУБД и структурированную БД (в отличие от ИС, использующих неструктурированные файлы или иные способы хранения).

### Особенности ИСБД
- Данные хранятся централизованно (или логически централизованно при распределённой БД) и структурированно.
- Доступ к данным осуществляется через СУБД, а не напрямую к файлам.
- Обеспечивается независимость прикладных программ от способа физического хранения данных.
- Поддерживается многопользовательский доступ с разграничением прав.

**Сравнение ИС и ИСБД:**

| Признак | ИС (общий случай) | ИСБД |
|---|---|---|
| Способ хранения данных | Может быть любым (файлы, БД и т.д.) | Обязательно структурированная БД |
| Наличие СУБД | Не обязательно | Обязательно |
| Целостность и непротиворечивость данных | Не гарантируется автоматически | Поддерживается средствами СУБД |
| Пример | Система учёта на разрозненных Excel-файлах | Система учёта на основе PostgreSQL/MySQL |

## 4. Система управления базой данных (СУБД)

**Определение.** СУБД — это комплекс программных и языковых средств, предназначенный для создания, ведения (наполнения, обновления) и совместного использования баз данных многими пользователями и приложениями, а также для обеспечения целостности, безопасности и эффективного доступа к данным.

### Основные функции СУБД
1. Управление данными во внешней памяти.
2. Управление буферами оперативной памяти.
3. Управление транзакциями (обеспечение свойств ACID: атомарность, согласованность, изолированность, долговечность; подробно — см. п. 11).
4. Журнализация и восстановление БД после сбоев.
5. Поддержание языков БД (DDL — язык определения данных, DML — язык манипулирования данными, например SQL).
6. Обеспечение защиты и разграничения прав доступа.

### Классификация СУБД

По **модели данных**: иерархические, сетевые, реляционные, объектно-ориентированные (см. п. 5).

По **степени распределённости**:
- Локальные (все компоненты на одном компьютере)
- Распределённые (данные и/или компоненты СУБД размещены на разных узлах)

По **способу доступа к БД**:
- Файл-серверные (Access — устаревший подход)
- Клиент-серверные (MySQL, PostgreSQL, Oracle, MS SQL Server)
- Встраиваемые (SQLite)

**Примечание/сравнение.** БД — это данные; СУБД — это инструмент управления этими данными; ИС — это система, использующая БД (через СУБД) для решения прикладных задач пользователя. Соотношение можно представить так:

`ИС ⊃ ИСБД ⊃ (СУБД + БД)`

## 5. Три математические модели данных

Исторически выделяют три классические математические (логические) модели организации данных в БД: **иерархическую**, **сетевую** и **реляционную**.

### 5.1. Иерархическая модель

**Определение.** Данные организованы в виде дерева (иерархии): каждый элемент (узел) имеет ровно одного «родителя» (кроме корневого) и может иметь несколько «потомков».

**Особенности:**
- Отношения между записями — только «один ко многим» (1:М).
- Быстрый доступ при движении по дереву сверху вниз.
- Проблема представления связей «многие ко многим» (M:N) — требует дублирования данных или искусственных узлов.
- Пример реализации: IMS (IBM), файловые системы, XML-документы.

### 5.2. Сетевая модель

**Определение.** Обобщение иерархической модели: узел (запись) может иметь **несколько родителей**, то есть данные представлены в виде произвольного графа связей.

**Особенности:**
- Поддерживает связи M:N напрямую (без дублирования данных).
- Более гибкая, чем иерархическая, но и более сложная в проектировании и навигации.
- Доступ к данным — навигационный (через явные указатели/цепочки), что требует от прикладного программиста знания физической структуры БД.
- Стандартизирована организацией CODASYL.

### 5.3. Реляционная модель

**Определение.** Данные представлены в виде совокупности двумерных таблиц (отношений), связанных между собой по значениям ключевых полей. Имеет строгое математическое обоснование на основе теории множеств и реляционной алгебры (Э. Кодд, 1970).

**Особенности:**
- Данные и связи между ними представлены единообразно — таблицами.
- Доступ к данным декларативный (через язык запросов, например SQL), а не навигационный.
- Поддерживает все типы связей: 1:1, 1:М, М:N (последняя — через промежуточную таблицу).
- Опирается на понятия: отношение, кортеж, атрибут, домен, первичный и внешний ключ, нормальные формы.

### Сравнение трёх моделей

| Критерий | Иерархическая | Сетевая | Реляционная |
|---|---|---|---|
| Структура | Дерево | Граф | Множество таблиц |
| Типы связей | Только 1:М | 1:М и M:N | 1:1, 1:М, M:N |
| Способ доступа | Навигационный | Навигационный | Декларативный (SQL) |
| Гибкость проектирования | Низкая | Средняя | Высокая |
| Математическая основа | Теория графов (деревья) | Теория графов | Теория множеств, реляционная алгебра |
| Независимость от физической структуры | Низкая | Низкая | Высокая |
| Современное применение | Ограничено (XML, реестры) | Редко | Широко (большинство СУБД) |

**Примечание.** Иногда к «трём моделям» также относят вместо сетевой — объектно-ориентированную или многомерную модель, в зависимости от учебной программы; в классической (исторической) трактовке речь идёт именно об иерархической, сетевой и реляционной моделях как о трёх этапах эволюции логических моделей данных.

## 6. Реляционная модель данных (подробно)

**Определение.** Реляционная модель данных — это способ организации данных в виде набора отношений (таблиц), где каждое отношение представляет собой множество кортежей (строк), а порядок строк и столбцов не имеет значения для модели.

### 6.1. Основные понятия

| Термин | Определение | Соответствие в таблице |
|---|---|---|
| Отношение (relation) | Математическое множество кортежей | Таблица |
| Кортеж (tuple) | Упорядоченный набор значений атрибутов | Строка (запись) |
| Атрибут (attribute) | Именованный столбец отношения | Столбец (поле) |
| Домен (domain) | Множество допустимых значений атрибута | Тип данных столбца |
| Степень отношения | Количество атрибутов | Количество столбцов |
| Мощность отношения | Количество кортежей | Количество строк |

### 6.2. Реляционные отношения

**Определение (математическое).** Пусть заданы множества (домены) D₁, D₂, …, Dₙ. **Отношением** R степени n называется подмножество декартова произведения этих множеств:

`R ⊆ D₁ × D₂ × … × Dₙ`

Иными словами, отношение — это некоторый набор n-ок (кортежей) `(d₁, d₂, …, dₙ)`, где `dᵢ ∈ Dᵢ`.

**Схема отношения** — это имя отношения и перечень его атрибутов с доменами: `R(A₁:D₁, A₂:D₂, …, Aₙ:Dₙ)`. Например:

`Студент(ID: Целое, ФИО: Строка, Группа: Строка, Дата_рождения: Дата)`

**Экземпляр отношения** — конкретное содержимое (набор кортежей) в данный момент времени. Схема меняется редко, экземпляр — постоянно (при каждой вставке, обновлении и удалении).

**Виды отношений в реляционных СУБД:**
- **Базовые (именованные)** — реально хранятся в БД (создаются `CREATE TABLE`).
- **Производные** — вычисляются через другие отношения и имеют имя (представления, `VIEW`).
- **Результаты запросов** — временные, неименованные отношения, возникающие при выполнении запроса.

**Чем отношение отличается от таблицы.** Таблица в СУБД — это «практическое воплощение» отношения, но с отклонениями от теории:

| Отношение (теория) | Таблица (SQL) |
|---|---|
| Множество: дубликатов нет | Могут быть одинаковые строки (если нет ключа) |
| Порядок кортежей не определён | Строки физически хранятся в каком-то порядке |
| Порядок атрибутов не важен | Столбцы имеют порядок в `CREATE TABLE` |
| Значения всегда определены | Допускается `NULL` (неопределённое значение) |

### 6.3. Заголовок и тело отношения

Каждое отношение состоит из двух частей:

- **Заголовок (heading)** — фиксированный набор пар «имя атрибута : домен». Это *структура* отношения, её схема. Заголовок не зависит от времени.
- **Тело (body)** — множество кортежей, каждый из которых соответствует заголовку (для каждого атрибута заголовка в кортеже есть ровно одно значение из его домена). Тело *изменяется во времени*.

**Пример.**

```
            ┌─ ЗАГОЛОВОК ─────────────────────────────────────┐
            │ ID:Целое   ФИО:Строка     Группа:Строка          │
            ├─ ТЕЛО ──────────────────────────────────────────┤
            │ 1          Иванов И.И.    ИВТ-21                 │
            │ 2          Петров П.П.    ИВТ-21                 │
            │ 3          Сидорова А.А.  ПМИ-22                 │
            └──────────────────────────────────────────────────┘
```

**Связь с характеристиками отношения:**
- **Степень** отношения определяется заголовком (здесь 3 атрибута).
- **Мощность** отношения определяется телом (здесь 3 кортежа).

### 6.4. Домен, атрибут, кортеж

**Домен** — множество допустимых значений, из которого атрибут может брать значения.
- Домен бывает **простым** (тип данных: целое, строка, дата) и **семантическим** (с «смыслом»: «Возраст» — целые числа от 0 до 150; «Оценка» — {2, 3, 4, 5}; «Код_группы» — строки по шаблону).
- Домен задаёт **допустимые операции и сравнения**: сравнивать имеет смысл только значения одного домена (нельзя осмысленно сравнить «Возраст» и «Вес», хотя оба — целые).
- В SQL домен реализуется типом данных и ограничениями: `INTEGER CHECK (age BETWEEN 0 AND 150)`; в некоторых СУБД (PostgreSQL) есть `CREATE DOMAIN`.

**Атрибут** — именованная характеристика сущности; формально — пара `(имя, домен)`.
- Имя атрибута уникально в пределах отношения.
- Разные атрибуты могут определяться на одном домене (например, `Дата_приёма` и `Дата_увольнения` — оба на домене «Дата»).

**Кортеж** — элемент отношения; множество пар `(атрибут, значение)`, по одной на каждый атрибут заголовка. В таблице это строка.

`t = ⟨ID: 1, ФИО: «Иванов И.И.», Группа: «ИВТ-21»⟩`

- Кортеж описывает один экземпляр сущности (один факт предметной области).
- Значение атрибута в кортеже принадлежит домену атрибута (или равно `NULL`, если это разрешено).
- Обращение к значению: `t.ФИО` или `t[ФИО]`.

### 6.5. Ключи
- **Первичный ключ (Primary Key, PK)** — атрибут (или набор атрибутов), однозначно идентифицирующий каждый кортеж; не может содержать NULL и должен быть уникальным.
- **Внешний ключ (Foreign Key, FK)** — атрибут, ссылающийся на первичный ключ другого (или того же) отношения; обеспечивает ссылочную целостность (referential integrity).
- **Потенциальный (возможный) ключ** — любой минимальный набор атрибутов, способный уникально идентифицировать кортеж; из потенциальных ключей выбирается один первичный.

### 6.6. Свойства отношений
1. Отсутствие дублирующихся кортежей (уникальность строк).
2. Отсутствие упорядоченности кортежей.
3. Отсутствие упорядоченности атрибутов.
4. Атомарность значений атрибутов (в классической, 1НФ-версии модели — каждое значение неделимо).

### 6.7. Целостность данных
- **Целостность сущностей** — первичный ключ не может быть NULL.
- **Целостность по ссылкам** — значение внешнего ключа либо NULL, либо совпадает с существующим значением первичного ключа связанного отношения (подробно — в п. 6.8).

### 6.8. Ссылочная целостность и механизм внешних ключей

**Определение.** **Ссылочная целостность** (referential integrity) — свойство БД, при котором каждая ссылка из одного отношения на другое указывает на реально существующий кортеж. Формально: для внешнего ключа FK дочернего отношения C, ссылающегося на первичный (или уникальный) ключ PK родительского отношения P, для каждого кортежа `c ∈ C` выполняется:

`c.FK = NULL` **или** существует `p ∈ P`, такой что `p.PK = c.FK`.

**Зачем нужна.** Без неё в БД появляются «висячие ссылки»: заказ, относящийся к несуществующему клиенту; оценка, выставленная несуществующему студенту.

**Внешний ключ (FOREIGN KEY) — механизм СУБД для поддержки ссылочной целостности.** Требования:
- FK и ключ, на который он ссылается, имеют **совместимые домены (типы)**;
- ссылаться можно на `PRIMARY KEY` или на столбцы с ограничением `UNIQUE`;
- FK может быть **составным** (несколько столбцов) и **самоссылающимся** (ссылка на ту же таблицу, например `manager_id` → `employee.id`);
- значение FK может быть `NULL`, если столбец это допускает (связь необязательна); для обязательной связи ставят `NOT NULL`.

**Пример.**

```sql
CREATE TABLE "group" (
    group_id INT PRIMARY KEY,
    name     VARCHAR(20) NOT NULL
);

CREATE TABLE student (
    id        INT PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    group_id  INT NOT NULL,
    FOREIGN KEY (group_id) REFERENCES "group"(group_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);
```

**Какие операции могут нарушить ссылочную целостность:**

| Операция | Когда нарушается |
|---|---|
| `INSERT` в дочернюю таблицу | FK указывает на несуществующий PK родителя |
| `UPDATE` FK в дочерней таблице | Новое значение отсутствует в родителе |
| `DELETE` из родительской таблицы | На удаляемую строку ещё ссылаются дочерние строки |
| `UPDATE` PK в родительской таблице | На старое значение PK ещё ссылаются дочерние строки |

**Как поддерживать целостность (стратегии при удалении/изменении в родителе):**

| Действие | Что делает СУБД |
|---|---|
| `NO ACTION` / `RESTRICT` | Запрещает операцию, если есть ссылающиеся строки (по умолчанию) |
| `CASCADE` | Каскадно удаляет (или обновляет) зависимые строки |
| `SET NULL` | Записывает `NULL` в FK зависимых строк (столбец должен допускать NULL) |
| `SET DEFAULT` | Записывает в FK значение по умолчанию |

**Практические рекомендации:**
- Объявлять внешние ключи декларативно (`FOREIGN KEY`), а не полагаться на проверки в приложении или триггеры.
- Создавать индекс на столбцах FK — это ускоряет соединения и проверки при удалении в родителе.
- Учитывать порядок: сначала вставлять строки в родительские таблицы, затем в дочерние; удалять — наоборот.
- `CASCADE` использовать осознанно: случайное удаление одной строки может удалить большой объём данных.

### 6.9. Нормализация (кратко)
Процесс приведения отношений к нормальным формам (1НФ, 2НФ, 3НФ, НФБК и др.) с целью устранения избыточности данных и аномалий вставки/обновления/удаления.

**Итоговое сравнение:** в отличие от иерархической и сетевой моделей, где связи задаются физически (указателями), в реляционной модели связи задаются **логически**, через совпадение значений ключей, что и обеспечивает её независимость от физического хранения и гибкость при изменении структуры БД.

## 7. Основы теории множеств в базах данных

Реляционная модель строится на теории множеств: отношение — это множество, а операции над отношениями — во многом операции над множествами.

### Базовые понятия
- **Множество** — совокупность различных объектов (элементов), рассматриваемая как единое целое. Обозначение: `A = {a, b, c}`.
- **Принадлежность:** `a ∈ A`; непринадлежность: `d ∉ A`.
- **Подмножество:** `A ⊆ B`, если каждый элемент A принадлежит B.
- **Пустое множество:** `∅` — не содержит элементов.
- **Мощность:** `|A|` — число элементов множества.
- Элементы множества **не упорядочены** и **не повторяются**: `{1, 2, 3} = {3, 2, 1} = {1, 1, 2, 3}`.

### Операции над множествами

| Операция | Обозначение | Результат |
|---|---|---|
| Объединение | `A ∪ B` | Элементы, принадлежащие A **или** B |
| Пересечение | `A ∩ B` | Элементы, принадлежащие A **и** B |
| Разность | `A \ B` (или `A − B`) | Элементы A, не принадлежащие B |
| Декартово произведение | `A × B` | Все упорядоченные пары `(a, b)`, `a ∈ A`, `b ∈ B`; `|A × B| = |A|·|B|` |

**Основные законы:**
- Коммутативность: `A ∪ B = B ∪ A`, `A ∩ B = B ∩ A` (разность — **не** коммутативна).
- Ассоциативность: `(A ∪ B) ∪ C = A ∪ (B ∪ C)`.
- Дистрибутивность: `A ∩ (B ∪ C) = (A ∩ B) ∪ (A ∩ C)`.
- Законы де Моргана: `¬(A ∪ B) = ¬A ∩ ¬B`, `¬(A ∩ B) = ¬A ∪ ¬B`.
- Пересечение выражается через разность: `A ∩ B = A − (A − B)`.

### Связь с базами данных

| Понятие теории множеств | Аналог в реляционной БД |
|---|---|
| Множество | Отношение (таблица без дубликатов) |
| Элемент множества | Кортеж (строка) |
| Декартово произведение доменов | Пространство всех возможных кортежей; отношение — его подмножество |
| Объединение, пересечение, разность | Операции `UNION`, `INTERSECT`, `EXCEPT` в SQL |
| Декартово произведение отношений | `CROSS JOIN` |
| Уникальность элементов | Первичный ключ, отсутствие дубликатов |

**Важное отличие.** В теории — множества (без повторов), а SQL работает с **мультимножествами** (bag): `UNION ALL` сохраняет дубликаты, а `UNION` (как и `SELECT DISTINCT`) их удаляет, приближая результат к «настоящему» множеству.

**Условие применимости.** Объединение, пересечение и разность применимы только к **совместимым по типу** отношениям: одинаковое число атрибутов и совпадающие домены соответствующих атрибутов.

## 8. Реляционная алгебра

**Определение.** Реляционная алгебра — это формальный (математический) язык запросов к реляционной БД: набор операций, каждая из которых принимает одно или два отношения и возвращает новое отношение. Предложена Э. Коддом (1970-е гг.) и является теоретической основой языка SQL.

### На чём основана
- на **теории множеств** (отношения — множества кортежей, операции объединения, пересечения, разности, декартова произведения);
- на **логике предикатов первого порядка** (условия выборки, соединения; её «декларативный» вариант — *реляционное исчисление*). **Теорема Кодда:** реляционная алгебра и реляционное исчисление равны по выразительной мощности.

### Основные принципы
1. **Замкнутость.** Результат любой операции — тоже отношение. Поэтому операции можно комбинировать в выражения любой вложенности: `π(σ(R ⋈ S))`.
2. **Процедурность.** Запрос — это последовательность операций, указывающая, *как* получить результат (в отличие от декларативного SQL и реляционного исчисления, где описывается, *что* нужно).
3. **Операции над множествами.** Операнды и результаты — множества кортежей, поэтому дубликаты автоматически устраняются.
4. **Реляционная полнота.** Любой язык, позволяющий выразить всё, что выражается в реляционной алгебре, называется реляционно полным; SQL этим свойством обладает.
5. **Минимальный базис.** Достаточно шести операций: выборка σ, проекция π, объединение ∪, разность −, декартово произведение ×, переименование ρ. Остальные (пересечение, соединение, деление) выражаются через них.

### Классификация операций

| Группа | Операции | Особенности |
|---|---|---|
| **Теоретико-множественные** | объединение ∪, пересечение ∩, разность −, декартово произведение × | Из теории множеств; первые три требуют совместимости отношений по типу |
| **Специальные реляционные** | выборка σ, проекция π, соединение ⋈, деление ÷ | Специфичны для реляционной модели (см. п. 9) |
| **Вспомогательные** | переименование ρ, присваивание ← | Удобство записи выражений |
| **Расширения** | группировка и агрегаты γ, внешние соединения, сортировка | Добавлены для практических нужд (SQL) |

### Соответствие алгебры и SQL

| Реляционная алгебра | SQL |
|---|---|
| `σ_условие(R)` | `SELECT * FROM R WHERE условие` |
| `π_A,B(R)` | `SELECT DISTINCT A, B FROM R` |
| `R ∪ S`, `R ∩ S`, `R − S` | `UNION`, `INTERSECT`, `EXCEPT` |
| `R × S` | `CROSS JOIN` |
| `R ⋈ S` | `JOIN` |
| `ρ_новое(R)` | `AS` (псевдоним) |

## 9. Специальные реляционные операции

Для примеров используем отношения:

**Студент**

| ID | ФИО | Группа_ID | Балл |
|---|---|---|---|
| 1 | Иванов | 10 | 85 |
| 2 | Петров | 10 | 60 |
| 3 | Сидорова | 20 | 92 |

**Группа**

| Группа_ID | Название |
|---|---|
| 10 | ИВТ-21 |
| 20 | ПМИ-22 |

### 9.1. Выборка (селекция, σ)

**Определение.** Выборка отбирает из отношения **кортежи (строки)**, удовлетворяющие условию. Схема (заголовок) результата не меняется.

`σ_условие(R)`

**Пример:** `σ_{Балл > 80}(Студент)` → строки с ID = 1 и ID = 3.

- Условие — логическое выражение из сравнений (`=, ≠, <, >, ≤, ≥`) и связок `∧` (И), `∨` (ИЛИ), `¬` (НЕ).
- Мощность результата ≤ мощности исходного отношения.
- SQL: `WHERE`.

### 9.2. Проекция (π)

**Определение.** Проекция оставляет в отношении только **указанные атрибуты (столбцы)**, а образовавшиеся дубликаты кортежей удаляет.

`π_{A₁, …, Aₖ}(R)`

**Пример:** `π_{Группа_ID}(Студент)` → `{10, 20}` (значение 10 встречается дважды, но в результате — один раз).

- Степень результата = числу перечисленных атрибутов.
- Мощность результата ≤ мощности исходного отношения (из-за удаления дубликатов).
- SQL: `SELECT DISTINCT столбцы` (без `DISTINCT` SQL дубликаты сохраняет).
- Операции комбинируются: `π_{ФИО}(σ_{Балл > 80}(Студент))` → Иванов, Сидорова.

### 9.3. Соединение (⋈)

**Определение.** Соединение объединяет кортежи двух отношений по условию, связывающему их атрибуты. Общая (θ-соединение) форма выражается через декартово произведение и выборку:

`R ⋈_θ S = σ_θ(R × S)`

**Разновидности:**

| Вид | Запись | Описание |
|---|---|---|
| **θ-соединение** | `R ⋈_θ S` | Условие θ — любое сравнение (`<`, `>`, `=` и др.) |
| **Эквисоединение** | `R ⋈_{R.A = S.B} S` | Условие — только равенство; в результате остаются оба столбца сравнения |
| **Естественное соединение** | `R ⋈ S` | Эквисоединение по **всем одноимённым атрибутам**; общий столбец в результате один |
| **Внешнее соединение** | ⟕, ⟖, ⟗ | Левое/правое/полное: сохраняет кортежи без пары, дополняя их `NULL` |
| **Полусоединение** | `R ⋉ S` | Кортежи R, для которых есть пара в S (столбцы только R) |

**Пример:** `Студент ⋈ Группа` (естественное, по `Группа_ID`):

| ID | ФИО | Группа_ID | Балл | Название |
|---|---|---|---|---|
| 1 | Иванов | 10 | 85 | ИВТ-21 |
| 2 | Петров | 10 | 60 | ИВТ-21 |
| 3 | Сидорова | 20 | 92 | ПМИ-22 |

SQL: `SELECT ... FROM Студент JOIN Группа ON Студент.Группа_ID = Группа.Группа_ID`. Соединение чаще всего выполняется по связке «внешний ключ — первичный ключ».

### 9.4. Деление (÷)

**Определение.** Пусть `R(A, B)` и `S(B)`. Деление `R ÷ S` возвращает множество значений A (атрибутов R, не входящих в S), которые в отношении R связаны **со всеми** кортежами из S.

**Выражение через основные операции:**

`R ÷ S = π_A(R) − π_A( (π_A(R) × S) − R )`

**Пример.** Отношение `Сдал(Студент, Предмет)` и `S = {БД, Алгебра}` — «обязательные предметы»:

| Студент | Предмет |
|---|---|
| Иванов | БД |
| Иванов | Алгебра |
| Петров | БД |
| Сидоров | БД |
| Сидоров | Алгебра |
| Сидоров | Физика |

`Сдал ÷ S` = `{Иванов, Сидоров}` — оба сдали и БД, и Алгебру. Петров сдал только БД, поэтому в результат не попал (лишний предмет «Физика» у Сидорова не мешает).

- Деление отвечает на запросы вида «найти всех, у кого есть **все** …».
- В SQL отдельного оператора нет; реализуется двойным `NOT EXISTS` или через `GROUP BY ... HAVING COUNT(...) = (SELECT COUNT(*) FROM S)`.

## 10. Поиск и доступ к данным БД

**Задача.** Найти нужные записи среди миллионов как можно быстрее, минимизируя число обращений к диску (именно они — главная «стоимость» операций в СУБД).

**Базовый способ — полный перебор (full scan):** последовательный просмотр всех записей таблицы. Сложность O(n); допустим для маленьких таблиц или когда нужна большая часть данных. Для ускорения используют сортировку, индексацию и хеширование.

### 10.1. Метод сортировки

**Идея.** Данные хранятся (или временно упорядочиваются) по значению ключа поиска, что позволяет применять **бинарный поиск** — O(log n) вместо O(n).

- **Упорядоченное хранение файла.** Записи физически отсортированы по ключу (в СУБД — *кластеризованное* хранение). Возможны эффективный поиск по значению и по диапазону (`BETWEEN`).
- **Недостатки:** вставка и удаление дороги (нужно сохранять порядок, сдвигать записи); физически таблица упорядочена только по **одному** ключу.
- **Внешняя сортировка.** Когда данные не помещаются в оперативную память, используют сортировку слиянием: исходные данные разбиваются на отсортированные «серии», затем они сливаются. Применяется для `ORDER BY`, `DISTINCT`, `GROUP BY`, соединения слиянием (merge join).

### 10.2. Метод индексации

**Индекс** — дополнительная структура данных, хранящая пары «значение ключа → указатель на запись», упорядоченные по ключу. Принцип тот же, что у предметного указателя в книге: сначала ищем в небольшом индексе, затем переходим сразу к нужной записи.

**Виды индексов:**

| Классификация | Виды |
|---|---|
| По отношению к данным | **Кластеризованный (первичный)** — определяет физический порядок записей, один на таблицу; **некластеризованный (вторичный)** — отдельная структура с указателями, их может быть много |
| По плотности | **Плотный** — запись для каждого значения ключа; **разреженный** — запись для блока данных |
| По структуре | B-дерево / B+-дерево, хеш-индекс, битовый (bitmap), полнотекстовый, пространственный (R-tree) |

**Основные структуры:**
- **B⁺-дерево** — сбалансированное многоветвистое дерево; стандарт для большинства СУБД. Поиск за O(log n), эффективно работает с диапазонами и сортировкой (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`).
- **Хеш-индекс** — значение ключа преобразуется хеш-функцией в адрес; поиск по равенству в среднем за O(1), но **не** поддерживает диапазоны и сортировку.
- **Битовый индекс** — для столбцов с малым числом различных значений (пол, статус).

**Составной индекс** по нескольким столбцам `(A, B)` эффективен для условий по `A` и по `A, B`, но, как правило, не помогает при условии только по `B` (правило левого префикса).

**Плюсы и минусы индексов:**
- ускоряют `SELECT`, `JOIN`, `ORDER BY`, проверку уникальности;
- замедляют `INSERT`, `UPDATE`, `DELETE` (индекс нужно обновлять);
- занимают дополнительное место на диске.

```sql
CREATE INDEX idx_student_group ON student (group_id);
CREATE UNIQUE INDEX idx_student_email ON student (email);
```

Индексы автоматически создаются для `PRIMARY KEY` и `UNIQUE`.

### 10.3. Сравнение методов

| Метод | Сложность поиска | Диапазонный поиск | Стоимость изменения данных |
|---|---|---|---|
| Полный перебор | O(n) | Да (но медленно) | Низкая |
| Сортировка (упорядоченный файл) | O(log n) | Да | Высокая |
| B⁺-индекс | O(log n) | Да | Средняя |
| Хеш-индекс | O(1) в среднем | Нет | Низкая |

## 11. Транзакции

**Определение.** Транзакция — это логическая единица работы с БД: последовательность операций (чтение, вставка, изменение, удаление), которая выполняется **как единое целое** — либо полностью (все операции применены), либо не выполняется вовсе (БД остаётся в прежнем состоянии). Транзакция переводит БД из одного согласованного состояния в другое.

**Классический пример — перевод денег между счетами:**

```sql
BEGIN;                                               -- начало транзакции
UPDATE account SET balance = balance - 500 WHERE id = 1;
UPDATE account SET balance = balance + 500 WHERE id = 2;
COMMIT;                                              -- фиксация
```

Если после первого `UPDATE` произойдёт сбой, без транзакции деньги «исчезнут». С транзакцией изменения откатятся (`ROLLBACK`).

### Операторы управления транзакциями
- `BEGIN` / `START TRANSACTION` — начало;
- `COMMIT` — фиксация: изменения становятся постоянными и видимыми другим;
- `ROLLBACK` — откат: все изменения транзакции отменяются;
- `SAVEPOINT` — точка сохранения внутри транзакции для частичного отката.

### Свойства ACID

| Свойство | Смысл | Чем обеспечивается |
|---|---|---|
| **Atomicity** (атомарность) | Все операции выполняются или ни одна | Журнал транзакций, откат |
| **Consistency** (согласованность) | Транзакция сохраняет ограничения целостности (ключи, FK, CHECK) | Ограничения БД, проверки |
| **Isolation** (изолированность) | Параллельные транзакции не влияют друг на друга | Блокировки, MVCC |
| **Durability** (долговечность) | После `COMMIT` данные не теряются даже при сбое | Журнал предзаписи (WAL), запись на диск |

### Проблемы параллельного выполнения
- **Потерянное обновление** — две транзакции меняют одну запись, и результат одной затирается.
- **«Грязное» чтение** — чтение данных, изменённых, но ещё не зафиксированных другой транзакцией (которая потом откатится).
- **Неповторяющееся чтение** — повторное чтение той же строки в рамках транзакции даёт другое значение.
- **Фантомное чтение** — повторный запрос по условию возвращает другой набор строк (появились или исчезли строки).

### Уровни изолированности (стандарт SQL)

| Уровень | «Грязное» чтение | Неповторяющееся чтение | Фантомы |
|---|---|---|---|
| `READ UNCOMMITTED` | возможно | возможно | возможны |
| `READ COMMITTED` | исключено | возможно | возможны |
| `REPEATABLE READ` | исключено | исключено | возможны* |
| `SERIALIZABLE` | исключено | исключено | исключены |

\* По стандарту; в некоторых СУБД (например, PostgreSQL) `REPEATABLE READ` фантомы тоже исключает.

Чем выше уровень изоляции, тем надёжнее данные, но ниже производительность из-за ожиданий и конфликтов.

### Механизмы реализации
- **Блокировки** (разделяемые — на чтение, исключительные — на запись; протокол двухфазной блокировки 2PL).
- **Многоверсионность (MVCC)** — читатели видят «снимок» данных и не блокируют писателей.
- **Журнал транзакций (WAL)** — изменения сначала записываются в журнал, что позволяет откатывать незавершённые и восстанавливать зафиксированные транзакции после сбоя.

## 12. Глоссарий

Термины расположены по алфавиту. В скобках указан раздел, где тема разобрана подробно.

| Термин | Определение |
|---|---|
| **ACID** | Набор свойств транзакции: атомарность, согласованность, изолированность, долговечность (п. 11) |

## 13. Важные замечания

**Различать понятия**
1. **БД ≠ СУБД ≠ ИС.** БД — данные; СУБД — программа для управления ими; ИС — вся система с интерфейсами, логикой и персоналом. Соотношение: `ИС ⊃ ИСБД ⊃ (СУБД + БД)`.
2. **Отношение ≠ таблица.** Отношение — множество (без дубликатов, без порядка, без `NULL` в теории); таблица SQL допускает дубликаты, порядок столбцов и `NULL`.
3. **Заголовок ≠ тело.** Заголовок (структура) почти не меняется, тело (данные) меняется постоянно. Степень определяется заголовком, мощность — телом.
4. **Домен ≠ тип данных.** Тип — техническое ограничение представления; домен — смысловое множество значений. Сравнивать осмысленно можно только значения одного домена.
5. **Первичный ключ ≠ внешний ключ.** PK идентифицирует строки своей таблицы; FK ссылается на строки другой таблицы (или той же).
6. **Потенциальный ключ ≠ суперключ.** Потенциальный ключ минимален: из него нельзя убрать атрибут без потери уникальности.

**Ключи и целостность**
7. Первичный ключ: уникальность **и** `NOT NULL`. Внешний ключ: `NULL` допустим (необязательная связь), если столбец это разрешает.
8. Ссылочная целостность может нарушаться четырьмя операциями: вставка и изменение FK в дочерней таблице, удаление и изменение PK в родительской.
9. `CASCADE` удобен, но опасен: одно удаление может стереть много связанных данных.
10. Связь «многие ко многим» в реляционной модели реализуется **через промежуточную таблицу** с двумя внешними ключами.
11. Индексируйте столбцы внешних ключей.

**Реляционная алгебра и SQL**
12. Алгебра оперирует **множествами**, SQL — **мультимножествами**. `SELECT` без `DISTINCT` сохраняет дубликаты, `UNION` их удаляет, `UNION ALL` сохраняет.
13. Объединение, пересечение и разность требуют **совместимых по типу** отношений (одинаковое число и домены атрибутов). Разность не коммутативна: `A − B ≠ B − A`.
14. Минимальный базис: `σ, π, ∪, −, ×, ρ`. Пересечение, соединение и деление через них выражаются: `A ∩ B = A − (A − B)`, `R ⋈_θ S = σ_θ(R × S)`.
15. Соединение — это выборка поверх декартова произведения; на практике СУБД не строит произведение целиком, а применяет оптимизированные алгоритмы (вложенные циклы, хеш, слияние).
16. Деление отвечает на вопросы «**все**…»; в SQL его нет, реализуют двойным `NOT EXISTS` или `GROUP BY ... HAVING COUNT(...)`.
17. Выборка меняет число строк, проекция — число столбцов (и может уменьшить число строк за счет удаления дубликатов).
18. Сравнение с `NULL` через `=` не работает: используйте `IS NULL` / `IS NOT NULL` (результат сравнения с `NULL` — «неизвестно»).

**Поиск и индексы**
19. Индекс ускоряет чтение, но замедляет запись и занимает место; индексировать всё подряд нельзя.
20. B⁺-дерево подходит для равенства и диапазонов; хеш-индекс — только для равенства.
21. Составной индекс `(A, B)` помогает при условиях по `A` и по `A, B`, но обычно не по одному `B`.
22. Кластеризованный индекс в таблице только один, некластеризованных может быть много.

**Транзакции**
23. `COMMIT` делает изменения постоянными, `ROLLBACK` отменяет; после `COMMIT` откат невозможен.
24. Повышение уровня изоляции повышает надежность данных, но снижает производительность.
25. Фантомы по стандарту возможны на `REPEATABLE READ`, но в отдельных СУБД (например, PostgreSQL) они на этом уровне исключены: поведение зависит от реализации.
26. Транзакция обеспечивает согласованность только относительно **объявленных** ограничений: если ограничение не задано (`FOREIGN KEY`, `CHECK`), СУБД не проверит его.
